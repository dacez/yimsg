## 2. 状态与维护规则

| 状态 | 含义 |
|---|---|
| `OPEN` | 已在真实 Chromium 稳定复现，尚无通过的正确期望回归 |
| `FIXED_PENDING_VERIFY` | 已有修复，但目标浏览器、性能门禁或全量回归尚未完成 |
| `CLOSED` | 正确期望的普通回归已通过，且没有 `test.fail` / `skip` / `fixme` 掩盖 |
| `DESIGN_EXPECTED` | 经契约确认属于设计行为，并保留重新定性的依据 |

新增缺陷时必须同时记录稳定编号、严重度、环境、前置条件、步骤、期望、实际、影响、定位和可执行回归。关闭缺陷时必须：

1. 保留原正确期望断言，移除临时 `test.fail`。
2. 同步本文总览、测试矩阵和设计契约；把复现、修复摘要与关闭证据归入 [`../../../../docs/archive/BoundedList缺陷列表.md`](../../../../docs/archive/BoundedList缺陷列表.md)。
3. 运行 35 项功能专项、6 项性能专项以及仓库全量测试；全量脚本通过 `run_component_tests.sh` 包含功能专项，但性能专项仍由 `run_performance_tests.sh` 独立执行。

产品缺陷继续使用 `BL-BUG-NNN`；测试夹具、调度和断言自身的缺陷使用 `BL-TEST-BUG-NNN`，不得把测试基础设施问题记成产品缺陷，也不得用降低 worker 或增加 retry 作为关闭依据。
