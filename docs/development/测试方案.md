## 1. 文档范围与口径

研发阶段，以当前分支代码为准。本文说明测试分层、执行入口和验证口径，目标是让测试说明与实现保持一致。

统计口径由 `tools/check_docs_consistency.sh` 统一输出；执行脚本后，在终端输出的“测试用例统计”段查看当前数量，文档不手写具体数量：

- Go 测试按 `func TestXxx` 统计。
- `server/tests/e2e/`、`cli/tests/e2e/` 与 `agent/tests/e2e/` 中的 `TestMain` 记为启动入口，不计入业务用例数。
- 前端测试按 `it(...)`/`test(...)` 统计。

## 3. 全量测试执行（推荐）

仓库已提供一键全量正确性门禁。脚本先准备依赖、刷新协议生成物并执行只读文档一致性校验，然后严格按以下分类顺序调用公开入口：

1. `./tools/run_unit_tests.sh`：Go 非 E2E、SDK 单元、UIKit 单元、Web 单元。
2. `./tools/run_integration_tests.sh`：SDK 与真实服务端集成。
3. `./tools/run_e2e_tests.sh`：Server、CLI、Agent E2E，以及 Playwright `chromium-e2e`。
4. `./tools/run_component_tests.sh`：Playwright `chromium-component`，包含 BoundedList 全部浏览器功能用例。

`./tools/run_performance_tests.sh` 是独立性能门禁，不进入 `run_all_tests.sh`。涉及 BoundedList 容量、虚拟窗口或性能路径的变更，必须在全量正确性门禁之外再执行性能入口。

命令：

```bash
./tools/run_all_tests.sh
```

各分类也可从仓库根目录独立执行：

| 分类 | 公开入口 | 独立运行行为 |
|---|---|---|
| 单元 | `./tools/run_unit_tests.sh` | 准备 Go / Node.js 依赖，运行全部非 E2E Go 测试和三组前端单元测试 |
| 集成 | `./tools/run_integration_tests.sh` | 未提供 `SERVER_WS_URL` 时自行构建并启动临时服务端 |
| E2E | `./tools/run_e2e_tests.sh` | 自行启动供 Server / CLI / Agent E2E 共用的临时服务；Web E2E 另用 Playwright 隔离环境 |
| 浏览器组件 | `./tools/run_component_tests.sh` | 跳过全局 seed、数据库和服务端，运行 `chromium-component` |
| 性能 | `./tools/run_performance_tests.sh` | 跳过全局 seed、数据库和服务端，以单 worker、零重试运行 `chromium-performance` |

根目录及 `apps/web` 工作区的 `npm run test:e2e`、`test:component`、`test:performance`、`test:ui` 均通过 `tools/scripts/run_playwright_tests.mjs` 跨平台设置项目和环境。`test:component`、`test:performance` 直接执行即为 standalone；`test:ui` 是兼容入口，当前覆盖 Web E2E + 浏览器组件共 195 项正确性测试，不包含性能项目。仓库级自动化和文档优先使用上表的分类 shell 入口，以便明确前置条件、服务生命周期和结果归属。

> 脚本已避免依赖 `mapfile` / `readarray` 等 Bash 4+ 内建，默认兼容 macOS 自带 Bash 3.2、常见 Linux 云主机 Bash 4+，以及 Git Bash / MSYS2 / Cygwin。

只读文档一致性校验也可单独执行：

```bash
./tools/check_docs_consistency.sh
```

协议生成物可单独刷新：

```bash
go run ./tools/cmd/protocolgen
```

协议生成物也可单独做只读校验：

```bash
go run ./tools/cmd/protocolgen --check
```

协议生成器读取 `protocol/yimsg.proto`，通过 `protoc-gen-go` 刷新 `protocol/generated/go/pb/yimsg.pb.go`，通过 `ts-proto` 刷新 `protocol/generated/typescript/yimsg.ts`。全量脚本会先安装固定版本的 `protoc-gen-go` 到 `$(go env GOPATH)/bin`，再在前端构建和服务端启动前执行刷新命令，保证临时环境和内存测试环境也能基于最新 protobuf 生成物运行；`type` 分发和 action 映射由服务端 WS 层、前端 transport 层的 switch 代码维护。

该脚本只读取仓库文件，不修改代码或文档，覆盖 `schema.go` ↔ schema 字段 / 索引对照、WebSocket action ↔ 接口总览、`YimsgClient` 公开方法 ↔ SDK 接口说明，以及 `docs/**/*.md` 的四行头部模板和相对链接。通过时会输出当前表数、字段数、索引数、WebSocket action 数、HTTP 接口数、SDK 公开方法数、文档文件数和测试用例统计，便于复核清单是否漂移。若文档内容有变动但 `最后复核` 日期未更新，脚本只输出提示，不阻断本地迭代。

验证路径选择：

| 变更范围 | 最小校验 | 说明 |
|---|---|---|
| 只改文档、索引、评价或历史内容处理规则 | `./tools/check_docs_consistency.sh` | 只读校验即可确认链接入口、头部模板和自动清单 |
| 改 action、schema、DAL、SDK API、UIKit / UI 行为、测试或生产代码 | `./tools/run_all_tests.sh` | 全量脚本已包含协议生成、文档一致性、unit、integration、E2E 和浏览器组件测试 |
| 改 BoundedList 大数据、窗口容量或性能敏感路径 | `./tools/run_all_tests.sh`，再执行 `./tools/run_performance_tests.sh` | 性能门禁保持独立，不能用全量正确性结果替代 |
| 数据库 schema 设计调整 | 先征求确认，再跑 `./tools/run_all_tests.sh` | 研发阶段直接修改当前 schema，不写 migration、`ALTER TABLE` 或旧数据兼容 |

> 全量脚本会自动按需安装 Playwright 浏览器并对网络环节重试，正常无需手动操作。
> 若需在新机器上补齐系统依赖（`libnss` 等），可在仓库根目录执行：
>
> ```bash
> npx playwright install --with-deps chromium
> ```
>
> 或运行全量脚本时设置 `YIMSG_PLAYWRIGHT_WITH_DEPS=1`。

### 3.1 测试提速（不降低强度）

全量脚本在保持测试覆盖与断言完全不变的前提下做了以下提速，核心思路是「去掉重复构建 + 降低与被测逻辑无关的固定成本 + 提高互不干扰用例的并行度」：

- **bcrypt 哈希成本**：脚本统一导出 `YIMSG_BCRYPT_COST=4`（`bcrypt.MinCost`），由 `server/internal/auth` 在进程启动时读取并覆盖默认的 `DefaultCost`。哈希算法与校验逻辑完全不变，仅去掉生产级抗暴力成本，使大量注册场景（Go 单测 `server/internal/service`、E2E、SDK 集成、Playwright 种子）的单次哈希从 ~67ms 降到 ~1ms。生产部署不设置该变量，保持 `DefaultCost`。
- **分类脚本复用**：独立运行集成或 E2E 分类时，脚本会自行构建并启动临时服务；`run_all_tests.sh` 则只准备一次前端构建和一个供 SDK 集成、Server / CLI / Agent E2E 复用的服务端。
- **共享服务端隔离**：SDK 集成与三组 Go E2E 共用的临时服务默认由操作系统分配空闲端口，并在启动后同时校验 HTTP 就绪和服务进程存活。全量入口会把 SDK 的 `SERVER_WS_URL` 固定为本轮服务地址，结束时只按本轮服务 PID 清理。并发运行多轮全量测试时，各轮使用独立端口、配置与数据目录，不会清理或误连另一轮服务；只有显式同时提供 `YIMSG_TEST_CONFIG`、`YIMSG_TEST_SERVER_HOST`、`YIMSG_TEST_SERVER_PORT` 时才复用指定服务。
- **Web E2E 隔离**：Playwright `globalSetup` 位于 `apps/web/tests/support/global-setup.ts`。它始终使用独立 seed、数据目录和操作系统分配的空闲端口启动 Web E2E 服务，并在 HTTP 就绪时复核服务进程仍存活，不能复用或误连集成测试的数据库进程；每次公开 Playwright 入口还会分配独立结果目录，避免并发任务互相清空截图和错误上下文。入口成功时清理自己的结果目录，失败时保留证据；显式提供 `PLAYWRIGHT_OUTPUT_DIR` 时由调用方管理。在全量脚本内仅通过 `YIMSG_SKIP_FRONTEND_BUILD=1` 与 `YIMSG_PREBUILT_SERVER` 复用前端产物和服务端二进制。直接运行公开 E2E 入口时会自动回退到本地构建。
- **UI 环境准备预算**：`globalSetup` 的测试数据生成与独立服务端构建各有 120 秒预算；二者仍以单次执行的退出码判定成败，不重试。该预算覆盖 Windows 并发 I/O 下的进程收尾，避免实际工作已完成却在 60 秒边界被误杀。
- **UI 资源清理**：E2E、组件和性能 spec 统一从 `tests/support/test-fixtures.ts` 引入 `test`。成功、断言失败或超时后，共享夹具先关闭每个 context 的页面，释放 worker、WebSocket 和 OPFS 资源；Playwright 内建 fixture 创建的默认 context 仍交还框架回收，测试手动创建的额外 context 再顺序关闭。页面和额外 context 的单次清理都有独立预算，避免 Windows 下浏览器资源阻塞整个 worker，同时不降低测试并发度。
- **跨端通知追平**：好友申请等跨页面流程先断言写入方接口成功，再让读取方切换视图触发主动拉取并轮询业务状态；通知仅作为变化提示，不把通知到达时序当作数据已经可见的唯一依据。
- **浏览器并行度**：Playwright 默认 `workers: '100%'`（按 CPU 核数并行，Playwright 默认仅用一半核数）。E2E 用例各自创建独立用户、互不共享状态；组件项目启用 `fullyParallel`；性能入口固定单 worker。可用 `PLAYWRIGHT_WORKERS` 覆盖非性能分类的 worker 数字或百分比。
- **异步 UI 断言**：显示名、虚拟窗口等会异步重渲染的界面必须轮询最终业务状态。分页测试以“可见数据集合出现新成员”证明翻页完成，不以可能在重渲染中归零的瞬时 `scrollTop` 作为成功条件。
- **UI 超时分层**：单用例总预算为 120 秒，覆盖并发 worker 的浏览器启动、`beforeEach`、测试体与夹具清理；具体业务状态继续使用 5–20 秒的局部断言超时。多阶段流程不会因基础设施启动抖动或局部超时之和超过总预算而在清理阶段误失败，真实状态卡死仍由对应的局部断言定位。
- **通知延迟追平**：好友请求等“写入 + 轻通知 + 主动拉取”流程不能依赖固定睡眠；测试会重新触发请求页拉取直到目标数据可见，并等待操作后的数据项消失确认写入完成。
- **高频不变量断言**：大量循环写入场景在每次迭代采样并累计最大值，循环结束后断言最大值；不得在热循环内重复调用测试框架 matcher，以免 matcher 开销挤占固定超时，同时仍保证任意一次越界都会被记录并失败。

上述变量仅作用于测试链路，不改动任何 schema、接口或生产默认配置。

### 3.2 网络健壮性（沙箱 / CI 优先）

在受限代理与沙箱网络下，下载类步骤最易因瞬时中断导致整轮失败。全量脚本针对此做了如下处理，目标是在不降低测试强度的前提下提升成功率与速度：

- **网络步骤统一重试**：`npm ci`、Playwright 浏览器安装、`go install protoc-gen-go`、`go mod download` 均走指数退避重试（2s/4s/8s/16s），可用 `YIMSG_NET_RETRY` 覆盖最大尝试次数（默认 4）。
- **Playwright 下载单次超时 + 自动切镜像**：每次 `playwright install chromium` 尝试都用 `timeout` 包裹，单次超过 `YIMSG_PLAYWRIGHT_DOWNLOAD_TIMEOUT`（默认 150s）未完成就直接放弃、转入下一次重试，不再傻等官方源自然超时/断连。调用方未显式设置 `PLAYWRIGHT_DOWNLOAD_HOST` 时，第 2 次起自动切换到 `npmmirror.com` 镜像；显式设置了该变量则全程尊重用户选择、不覆盖。
- **依赖已具备则跳过**：`protoc-gen-go` 命中目标版本即跳过安装；Playwright 通过实际无头启动探针判断浏览器是否就绪，就绪则不再联网安装，显著缩短重复运行耗时。
- **改用完整 chromium 构建**：`playwright.config.ts` 的 chromium 项设置 `channel: 'chromium'`，以完整 chromium 构建运行新版无头模式，不依赖单独的 `chrome-headless-shell` 二进制——后者是额外大体积下载，在受限代理下最易被中断。因此 Playwright 安装**以浏览器能否启动为成败判据**，而非 `playwright install` 的退出码，避免被 `chrome-headless-shell` 下载失败误伤整轮 UI 测试。
- **可选跳过浏览器安装**：设置 `PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1` 或 `YIMSG_SKIP_PLAYWRIGHT_INSTALL=1` 时跳过浏览器安装（适用于已预装匹配版本的环境）。
- **Windows 下浏览器安装目录固定到 `%LOCALAPPDATA%` 之外**：部分 Windows 环境的 `%LOCALAPPDATA%` 会被宿主打包机制静默重定向（例如指向 `...\Packages\<PackageFamilyName>\LocalCache\Local\...`），普通文件 API 能透明读到重定向后的内容，但 `chrome.exe` 依赖的 side-by-side 清单加载走另一套路径解析，找不到该目录下的清单文件，导致启动报 `"side-by-side configuration is incorrect"`（与系统是否装有 VC++ 运行库无关）。全量脚本在 Windows 下、调用方未显式设置 `PLAYWRIGHT_BROWSERS_PATH` 时，固定改用 `C:/ms-playwright-browsers` 安装浏览器，避开该重定向。

## 5. 与代码保持一致的执行要求

- 提交前应至少执行一次 `./tools/run_all_tests.sh`。

## 6. BoundedList Playwright 与性能专项

### 6.1 目标、环境与测试工程

BoundedList 是 UIKit 所有大列表的目标统一组件。Vitest 负责数据窗口和编排逻辑的快速单元回归；本专项必须在真实 Chromium 中补齐浏览器才具备的 DOM 尺寸、滚动锚点、焦点、指针、事件委托、动画帧、垃圾回收和性能行为。

| 项目 | 口径 |
|---|---|
| 功能 spec | `apps/web/tests/component/bounded-list.spec.ts` |
| 性能 spec | `apps/web/tests/performance/bounded-list.performance.spec.ts` |
| 浏览器 harness | `apps/web/tests/support/bounded-list/browser-harness.ts` |
| Playwright fixture | `apps/web/tests/support/bounded-list/fixture.ts` |
| 已验证浏览器 | Chromium `149.0.7827.55` |
| 已验证 Playwright | `1.61.1` |
| 数据依赖 | harness 用 `route.fulfill` 提供确定性页面与数据；专项模式不需要账号、数据库、seed 或服务端 |
| 当前结果 | 功能 50 项全部 PASS；性能 6 项全部 PASS；合计 56 项，0 个当前已知失败，`BL-BUG-001`～`014` 均为 CLOSED |
| 缺陷事实源 | [`packages/uikit/docs/boundedlist/缺陷列表.md`](../../packages/uikit/docs/boundedlist/缺陷列表.md) |

所有 Playwright 分类在配置和公开入口上均固定 `retries: 0`。组件项目启用 `fullyParallel`；性能项目固定 `fullyParallel: false`、单 worker、单用例预算 120 秒：同一文件中的门禁顺序执行，但一项失败不会阻止其余项继续收集结果。性能结果以浏览器页内 `performance.now()` 采样，避免把 Playwright driver 往返和服务端启动时间混入组件耗时。

并发稳定性证据同样不靠重试或降低 worker：`fullyParallel`、4 workers、`retries=0` 的功能专项当前为 50/50，0 fail、0 retry。当前 BoundedList 功能专项为 50 项，并继续使用同一 `fullyParallel`、零重试入口。

### 6.2 数据级别

| 级别 | 数据量 / 组合 | 验证目的 |
|---|---|---|
| `D0` | 0 条 | 初始 loading、确认空态、过滤空态、空页收敛 |

| `D100K` | 100,000 条 | 本地全量加载、过滤和排序的首屏性能 |

所有数据量测试都同时断言组件状态 `count` 和真实 `[data-bsw-key]` DOM 行数。只测接口返回数量、只测滚动条位置或只测执行耗时，都不能证明 BoundedList 有界。

### 6.5 性能矩阵与阈值

性能 spec 每项都会把数据规模、页配置、浏览器 user agent、硬件并发度、计时摘要和可用的堆数据作为 JSON attachment 加入 Playwright 结果。首轮或前若干轮只作预热，不进入 P95。

| ID | 场景 | 采样与预热 | 容量断言 | 时间 / 内存阈值 | 当前状态 |
|---|---|---|---|---|---|
| `BL-PERF-001` | 本地 100,000 条过滤排序首屏 | 21 轮，首轮预热，20 个有效样本 | `count≤200`、DOM≤200 | P95≤1500ms | PASS |
| `BL-PERF-002` | 逻辑 1,000,000 条连续 forward 250 页 | 250 页，前 10 页预热 | `count=500`、DOM=500、251 次请求，首尾 identity=`24600` / `25099` | 单页 P95≤100ms、max≤250ms | PASS |
| `BL-PERF-003` | 200 行窗口连续 patch 200 次 | 200 次，前 20 次预热 | 最终 count=200、DOM=200 | P95≤50ms、max≤200ms | PASS |
| `BL-PERF-004` | 同一任务 10,000 次 invalidate | 单任务入队，等待 2 帧和 idle | 只触发 1 次追平请求；count=100、DOM=100 | 10,000 次入队≤500ms | PASS |

### 6.6 执行命令与项目依赖

组件与性能公开入口均设置 `BOUNDED_LIST_STANDALONE=1`，不启动全局 seed、前端构建和服务端，适合开发中快速复现。以下命令从仓库根目录执行：

```bash
# 功能契约：真实 Chromium、零重试；默认按可用 CPU 并行
./tools/run_component_tests.sh

# 性能 / 容量：独立性能项目，串行、单 worker、零重试
./tools/run_performance_tests.sh
```

Playwright 配置具有三个互不混跑的项目：

| 项目 | 匹配范围 | 环境与并发 |
|---|---|---|
| `chromium-e2e` | `e2e/**/*.spec.ts` | 使用 `tests/support/global-setup.ts` 创建独立 seed、数据目录、操作系统空闲端口和服务端；零重试 |
| `chromium-component` | `component/**/*.spec.ts` | 由组件入口跳过全局环境，`fullyParallel`、零重试 |
| `chromium-performance` | `performance/**/*.performance.spec.ts` | 由性能入口跳过全局环境，单 spec 串行、单 worker、零重试 |

`BOUNDED_LIST_STANDALONE=1` 只用于独立 browser harness，用来跳过全局 setup / teardown。组件分类保持并行以暴露竞态；性能分类由公开脚本和 npm 命令双重固定单 worker。项目之间没有隐式依赖，分类入口只执行自己的目录。

最终合并前必须从仓库根目录执行：

```bash
./tools/run_all_tests.sh
```

全量脚本按 unit → integration → E2E → component 顺序执行；其中 `run_component_tests.sh` 只运行 `chromium-component`，因此 53 个 BoundedList 功能用例执行一次且不会带上性能项目。6 个 BoundedList 性能用例必须使用独立性能入口执行；性能专项通过不能替代全量结果，全量通过也不能替代性能专项结果。

### 6.7 缺陷回归政策与通过标准

1. 当前 50 项功能与 6 项性能回归全部为普通 PASS，用例中没有 `test.fail`、`skip` 或 `fixme`。
2. 每个真实浏览器缺陷使用 `BL-BUG-NNN` 编号；同一缺陷可有多条回归，例如 `BL-BUG-010` 同时由功能去重和性能硬预算约束。
3. 新缺陷只有在缺陷列表登记为 OPEN、拥有稳定复现步骤和正确期望断言后，才可临时使用 `test.fail`；禁止用 `skip`、`fixme`、删除测试、放宽 DOM / count 上限或吞错替代。
4. 修复时必须移除 `test.fail`，保留正确断言，更新缺陷状态，并运行 `./tools/run_all_tests.sh` 与 `./tools/run_performance_tests.sh`；对应结果仍须包含 50 项功能和 6 项性能回归。
5. 专项通过标准是 56 项全部 PASS，且不存在 pageerror、未处理 Promise 拒绝、容量越界或性能阈值退化。
