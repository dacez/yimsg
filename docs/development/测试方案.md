## 3. 全量测试执行（推荐）

仓库已提供一键全量脚本，包含：

1. 构建并启动服务端
2. 刷新协议生成物
3. 执行只读文档一致性校验
4. 执行 Go 非 E2E 测试
5. 执行 Go E2E 测试
6. 执行前端 unit / sdk / ui 测试

命令：

```bash
./tools/run_all_tests.sh
```

> 脚本已避免依赖 `mapfile` / `readarray` 等 Bash 4+ 内建，默认兼容 macOS 自带 Bash 3.2、常见 Linux 云主机 Bash 4+，以及 Git Bash / MSYS2 / Cygwin。

只读文档一致性校验也可单独执行：

```bash
./tools/check_docs_consistency.sh
```

协议生成物可单独刷新：

```bash
go run ./tools/cmd/protocolgen
```

协议生成物也可单独做只读校验：

```bash
go run ./tools/cmd/protocolgen --check
```

协议生成器读取 `protocol/yimsg.proto`，通过 `protoc-gen-go` 刷新 `protocol/generated/go/pb/yimsg.pb.go`，通过 `ts-proto` 刷新 `protocol/generated/typescript/yimsg.ts`。全量脚本会先安装固定版本的 `protoc-gen-go` 到 `$(go env GOPATH)/bin`，再在前端构建和服务端启动前执行刷新命令，保证临时环境和内存测试环境也能基于最新 protobuf 生成物运行；`type` 分发和 action 映射由服务端 WS 层、前端 transport 层的 switch 代码维护。

该脚本只读取仓库文件，不修改代码或文档，覆盖 `schema.go` ↔ schema 字段 / 索引对照、WebSocket action ↔ 接口总览、`YimsgClient` 公开方法 ↔ SDK 接口说明，以及 `docs/**/*.md` 的四行头部模板和相对链接。通过时会输出当前表数、字段数、索引数、WebSocket action 数、HTTP 接口数、SDK 公开方法数、文档文件数和测试用例统计，便于复核清单是否漂移。若文档内容有变动但 `最后复核` 日期未更新，脚本只输出提示，不阻断本地迭代。

验证路径选择：

| 变更范围 | 最小校验 | 说明 |
|---|---|---|
| 只改文档、索引、评价或历史内容处理规则 | `./tools/check_docs_consistency.sh` | 只读校验即可确认链接入口、头部模板和自动清单 |
| 改 action、schema、DAL、SDK API、UIKit / UI 行为、测试或生产代码 | `./tools/run_all_tests.sh` | 全量脚本已包含协议生成、文档一致性校验、后端测试、E2E、前端 unit / sdk / ui |
| 数据库 schema 设计调整 | 先征求确认，再跑 `./tools/run_all_tests.sh` | 研发阶段直接修改当前 schema，不写 migration、`ALTER TABLE` 或旧数据兼容 |

> 全量脚本会自动按需安装 Playwright 浏览器并对网络环节重试，正常无需手动操作。
> 若需在新机器上补齐系统依赖（`libnss` 等），可在仓库根目录执行：
>
> ```bash
> npx playwright install --with-deps chromium
> ```
>
> 或运行全量脚本时设置 `YIMSG_PLAYWRIGHT_WITH_DEPS=1`。

### 3.1 测试提速（不降低强度）

全量脚本在保持测试覆盖与断言完全不变的前提下做了以下提速，核心思路是「去掉重复构建 + 降低与被测逻辑无关的固定成本 + 提高互不干扰用例的并行度」：

- **bcrypt 哈希成本**：脚本统一导出 `YIMSG_BCRYPT_COST=4`（`bcrypt.MinCost`），由 `server/internal/auth` 在进程启动时读取并覆盖默认的 `DefaultCost`。哈希算法与校验逻辑完全不变，仅去掉生产级抗暴力成本，使大量注册场景（Go 单测 `server/internal/service`、E2E、SDK 集成、Playwright 种子）的单次哈希从 ~67ms 降到 ~1ms。生产部署不设置该变量，保持 `DefaultCost`。
- **构建产物复用**：脚本只构建一次前端 `web/` 和服务端二进制；Playwright `globalSetup` 通过 `YIMSG_SKIP_FRONTEND_BUILD=1` 跳过重复的 `npm run build`，通过 `YIMSG_PREBUILT_SERVER` 复用脚本已编译的服务端二进制，避免重复 `go build`。单独运行 `npm run test:ui` 时不设置这两个变量，会自动回退到本地构建。
- **UI 环境准备预算**：`globalSetup` 的测试数据生成与独立服务端构建各有 120 秒预算；二者仍以单次执行的退出码判定成败，不重试。该预算覆盖 Windows 并发 I/O 下的进程收尾，避免实际工作已完成却在 60 秒边界被误杀。
- **UI 资源清理**：共享夹具在每个用例后先关闭 context 内页面，再顺序关闭各 context；测试 worker 仍保持并发运行，避免 Windows 下多个 Chromium context 同时销毁时互相等待并级联触发 worker 重启。
- **跨端通知追平**：好友申请等跨页面流程先断言写入方接口成功，再让读取方切换视图触发主动拉取并轮询业务状态；通知仅作为变化提示，不把通知到达时序当作数据已经可见的唯一依据。
- **UI 并行度**：`playwright.config.ts` 默认 `workers: '100%'`（按 CPU 核数并行，Playwright 默认仅用一半核数）。UI 用例各自创建独立用户、互不共享状态，可用 `PLAYWRIGHT_WORKERS` 覆盖（数字或百分比）。
- **UI 上下文隔离**：所有 UI spec 统一从 `tests/ui/test-fixtures.ts` 引入 `test`；共享 `afterEach` 会在成功、断言失败或超时后并发关闭当前 worker 的全部 BrowserContext，避免失败用例把页面、连接与浏览器资源泄漏给同一 worker 的后续用例。
- **异步 UI 断言**：显示名、虚拟窗口等会异步重渲染的界面必须轮询最终业务状态。分页测试以“可见数据集合出现新成员”证明翻页完成，不以可能在重渲染中归零的瞬时 `scrollTop` 作为成功条件。
- **UI 超时分层**：单用例总预算为 120 秒，覆盖并发 worker 的浏览器启动、`beforeEach`、测试体与夹具清理；具体业务状态继续使用 5–20 秒的局部断言超时。多阶段流程不会因基础设施启动抖动或局部超时之和超过总预算而在清理阶段误失败，真实状态卡死仍由对应的局部断言定位。
- **通知延迟追平**：好友请求等“写入 + 轻通知 + 主动拉取”流程不能依赖固定睡眠；测试会重新触发请求页拉取直到目标数据可见，并等待操作后的数据项消失确认写入完成。
- **高频不变量断言**：大量循环写入场景在每次迭代采样并累计最大值，循环结束后断言最大值；不得在热循环内重复调用测试框架 matcher，以免 matcher 开销挤占固定超时，同时仍保证任意一次越界都会被记录并失败。

上述变量仅作用于测试链路，不改动任何 schema、接口或生产默认配置。

### 3.2 网络健壮性（沙箱 / CI 优先）

在受限代理与沙箱网络下，下载类步骤最易因瞬时中断导致整轮失败。全量脚本针对此做了如下处理，目标是在不降低测试强度的前提下提升成功率与速度：

- **网络步骤统一重试**：`npm ci`、Playwright 浏览器安装、`go install protoc-gen-go`、`go mod download` 均走指数退避重试（2s/4s/8s/16s），可用 `YIMSG_NET_RETRY` 覆盖最大尝试次数（默认 4）。
- **Playwright 下载单次超时 + 自动切镜像**：每次 `playwright install chromium` 尝试都用 `timeout` 包裹，单次超过 `YIMSG_PLAYWRIGHT_DOWNLOAD_TIMEOUT`（默认 150s）未完成就直接放弃、转入下一次重试，不再傻等官方源自然超时/断连。调用方未显式设置 `PLAYWRIGHT_DOWNLOAD_HOST` 时，第 2 次起自动切换到 `npmmirror.com` 镜像；显式设置了该变量则全程尊重用户选择、不覆盖。
- **依赖已具备则跳过**：`protoc-gen-go` 命中目标版本即跳过安装；Playwright 通过实际无头启动探针判断浏览器是否就绪，就绪则不再联网安装，显著缩短重复运行耗时。
- **改用完整 chromium 构建**：`playwright.config.ts` 的 chromium 项设置 `channel: 'chromium'`，以完整 chromium 构建运行新版无头模式，不依赖单独的 `chrome-headless-shell` 二进制——后者是额外大体积下载，在受限代理下最易被中断。因此 Playwright 安装**以浏览器能否启动为成败判据**，而非 `playwright install` 的退出码，避免被 `chrome-headless-shell` 下载失败误伤整轮 UI 测试。
- **可选跳过浏览器安装**：设置 `PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1` 或 `YIMSG_SKIP_PLAYWRIGHT_INSTALL=1` 时跳过浏览器安装（适用于已预装匹配版本的环境）。
- **Windows 下浏览器安装目录固定到 `%LOCALAPPDATA%` 之外**：部分 Windows 环境的 `%LOCALAPPDATA%` 会被宿主打包机制静默重定向（例如指向 `...\Packages\<PackageFamilyName>\LocalCache\Local\...`），普通文件 API 能透明读到重定向后的内容，但 `chrome.exe` 依赖的 side-by-side 清单加载走另一套路径解析，找不到该目录下的清单文件，导致启动报 `"side-by-side configuration is incorrect"`（与系统是否装有 VC++ 运行库无关）。全量脚本在 Windows 下、调用方未显式设置 `PLAYWRIGHT_BROWSERS_PATH` 时，固定改用 `C:/ms-playwright-browsers` 安装浏览器，避开该重定向。

## 7. BoundedList Playwright 与性能专项

### 7.1 目标、环境与测试工程

BoundedList 是 UIKit 所有大列表的目标统一组件。Vitest 负责数据窗口和编排逻辑的快速单元回归；本专项必须在真实 Chromium 中补齐浏览器才具备的 DOM 尺寸、滚动锚点、焦点、指针、事件委托、动画帧、垃圾回收和性能行为。

| 项目 | 口径 |
|---|---|
| 功能 spec | `apps/web/tests/ui/bounded-list/bounded-list.spec.ts` |
| 性能 spec | `apps/web/tests/ui/bounded-list/bounded-list.performance.spec.ts` |
| 浏览器 harness | `apps/web/tests/ui/bounded-list/browser-harness.ts` |
| Playwright fixture | `apps/web/tests/ui/bounded-list/fixture.ts` |
| 已验证浏览器 | Chromium `149.0.7827.55` |
| 已验证 Playwright | `1.61.1` |
| 数据依赖 | harness 用 `route.fulfill` 提供确定性页面与数据；专项模式不需要账号、数据库、seed 或服务端 |
| 当前结果 | 功能 34 项：23 项正常通过、11 项已知失败；性能 6 项：5 项正常通过、1 项复用 `BL-BUG-010` 做容量回归；合计 40 项、11 个唯一已知缺陷 |
| 缺陷事实源 | [`packages/uikit/docs/boundedlist/缺陷列表.md`](../../packages/uikit/docs/boundedlist/缺陷列表.md) |

功能 spec 在 describe 级固定 `retries: 0`。性能项目固定 `fullyParallel: false`、`retries: 0`、单用例预算 120 秒：同一文件中的门禁顺序执行，但一项失败不会阻止其余项继续收集结果。性能结果以浏览器页内 `performance.now()` 采样，避免把 Playwright driver 往返和服务端启动时间混入组件耗时。

### 7.5 性能矩阵与阈值

性能 spec 每项都会把数据规模、页配置、浏览器 user agent、硬件并发度、计时摘要和可用的堆数据作为 JSON attachment 加入 Playwright 结果。首轮或前若干轮只作预热，不进入 P95。

| ID | 场景 | 采样与预热 | 容量断言 | 时间 / 内存阈值 | 当前状态 |
|---|---|---|---|---|---|
| `BL-PERF-001` | 本地 100,000 条过滤排序首屏 | 21 轮，首轮预热，20 个有效样本 | `count≤200`、DOM≤200 | P95≤1500ms | PASS |
| `BL-PERF-002` | 逻辑 1,000,000 条连续 forward 250 页 | 250 页，前 10 页预热 | `count=500`、DOM=500、251 次请求，首尾 identity=`24600` / `25099` | 单页 P95≤100ms、max≤250ms | PASS |
| `BL-PERF-003` | 200 行窗口连续 patch 200 次 | 200 次，前 20 次预热 | 最终 count=200、DOM=200 | P95≤50ms、max≤200ms | PASS |
| `BL-PERF-004` | 同一任务 10,000 次 invalidate | 单任务入队，等待 2 帧和 idle | 只触发 1 次追平请求；count=100、DOM=100 | 10,000 次入队≤500ms | PASS |
| `BL-PERF-005` | 创建并 dispose 300 次 | 先预热 20 次；CDP 强制 GC 前后取样 | 注册表为空、`.bl-case` 为 0 | GC 后堆增长≤16MiB | PASS |
| `BL-PERF-006` | 连续 1,000 次 `upsertLocal` | 单轮连续插入并强制布局 | `count≤200`、DOM≤200 | 容量是硬门禁，耗时作为 attachment 记录 | KNOWN_FAIL `BL-BUG-010` |

性能阈值只允许在有明确硬件 / 浏览器差异证据时调整。阈值调整必须在同一变更中保留调整前后记录、原因和新的实测基线；不得因为实现退化或 CI 偶发失败直接放宽。DOM / count 上限属于功能不变量，不能按机器性能放宽。

### 7.6 执行命令与项目依赖

独立专项不启动全局 seed、构建和服务端，适合开发中快速复现。以下命令从仓库根目录执行：

```bash
# 功能契约：真实 Chromium，单 worker，无 retry
BOUNDED_LIST_STANDALONE=1 PLAYWRIGHT_WORKERS=1 \
  npm run test:ui -w @yimsg/web -- \
  tests/ui/bounded-list/bounded-list.spec.ts --project=chromium --workers=1

# 性能 / 容量：独立性能项目，串行、单 worker、无 retry
BOUNDED_LIST_STANDALONE=1 PLAYWRIGHT_WORKERS=1 \
  npm run test:ui -w @yimsg/web -- \
  tests/ui/bounded-list/bounded-list.performance.spec.ts \
  --project=chromium-bounded-list-performance --workers=1

# 两份专项一起运行
BOUNDED_LIST_STANDALONE=1 PLAYWRIGHT_WORKERS=1 \
  npm run test:ui -w @yimsg/web -- tests/ui/bounded-list --workers=1
```

常规 Playwright 配置具有两个项目：

| 项目 | 匹配范围 | 依赖与并发 |
|---|---|---|
| `chromium` | 除 `*.performance.spec.ts` 外的全部 UI spec | 常规 UI 项目；BoundedList 功能 describe 自行关闭 retry |
| `chromium-bounded-list-performance` | 仅 `*.performance.spec.ts` | 常规模式依赖 `chromium`，等普通 Chromium 回归通过后执行；单 spec 串行、无 retry |

`BOUNDED_LIST_STANDALONE=1` 只用于独立 browser harness：它取消性能项目对全量 `chromium` 项目的依赖、跳过全局 setup / teardown，并在配置层强制单 worker，避免调用者漏传 `--workers=1` 时让功能项目与性能项目争抢 CPU。默认配置和全量脚本不设置该变量，仍会先准备并验证完整产品环境。

最终合并前必须从仓库根目录执行：

```bash
./tools/run_all_tests.sh
```

全量脚本会运行普通 Chromium UI 项目和其后的 BoundedList 性能项目。独立专项通过不能替代全量结果。

### 7.7 已知失败政策与通过标准

1. 只有已在 [`BoundedList 缺陷列表`](../../packages/uikit/docs/boundedlist/缺陷列表.md) 登记为 OPEN、拥有稳定复现步骤和明确期望断言的缺陷，才允许使用 `test.fail`。
2. 每个唯一缺陷使用 `BL-BUG-NNN` 编号；一个缺陷可在功能和性能 spec 各有一条回归，例如 `BL-BUG-010`，但两处必须引用同一缺陷。
3. `test.fail` 必须保留正确产品期望，不能把当前错误行为写成断言。已知失败若意外通过，Playwright 会让用例失败，提醒维护者移除标记并复测关闭缺陷。
4. 禁止用 `skip`、`fixme`、删除测试、放宽 DOM / count 上限或吞掉错误代替 `test.fail`。
5. 修复时在同一变更中移除对应 `test.fail`、保留原断言、更新缺陷状态，并运行定向专项与 `./tools/run_all_tests.sh`。
6. 专项通过标准是：所有非 `test.fail` 用例通过；所有 `test.fail` 按预期失败；不存在 unexpected pass、unexpected failure、pageerror、未处理 Promise 拒绝或性能阈值退化。
