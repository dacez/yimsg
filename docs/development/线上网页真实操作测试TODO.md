### BUG-001 [P1] Persistent 模式好友申请与接受结果不增量同步

- 环境：`https://yimsg.im/app/`，代码基线 `2f1961d`；A 为 Persistent/Desktop，B、C 为 Instant。
- 账号：A `qa260726a7421`，B `qa260726b7421`。
- 前置条件：A、B 均为新注册且无好友。
- 步骤：
  1. A 搜索 B，填写备注 `B-测试好友` 并发送申请。
  2. A 打开“Requests”；B 打开“Requests”并接受。
  3. A 等待同步状态结束，切换 Requests / Friends 强制重新拉取。
  4. A 在 Settings 执行 Clear Data，再回到 Friends。
- 期望：A 发送后看到不可操作的已发申请；B 接受后 A、B 无需清本地库即可互相出现在好友列表。
- 实际：A 的已发申请始终为空；B 接受后 B 立即看到 A，A 的好友列表仍为空。A 执行 Clear Data 后，B 才以备注 `B-测试好友` 出现在 A 好友列表。
- 复现率：1/1；对照组 C（Instant）发送给 D 后，C 的已发申请可正常显示。
- 影响：Persistent 用户无法可靠看到好友申请和接受结果，好友主链路在普通刷新操作下表现失败；清除全部本地数据是破坏性较强的临时绕过。
- 初步定位：Persistent DataGateway 的联系人增量同步或好友通知后的主动拉取链路。
- 2026-07-27 复测补充：
  - 基线：`ac49333`；A `qa260726r2a9153`、B `qa260726r2b9153`、C `qa260726r2c9153`。
  - A、B、C 分别出现好友列表为空或 `Failed to load contacts`；只读检查服务端数据库确认 A、B、C 的好友和组织通讯录行仍然完整。
  - A、C 执行 Clear Data 后重新全量同步，联系人立即恢复，进一步确认故障位于 Persistent 本地副本而非服务端数据。
  - 当前联系人页面只显示通用错误并吞掉底层查询异常，因此仅凭页面和服务端日志还不能确定是本地 SQLite 打开、查询还是同步游标失效；修复时需要保留并上报原始 DataGateway 错误，同时在副本不可用时提供自动重建路径。

### 已撤销 BUG-014：同一浏览器上下文共享持久登录态属于设计预期

- 原环境：`https://yimsg.im/app/`，代码基线 `2f1961d`；在同一无痕浏览器上下文的不同标签页中分别登录 B、D。

  1. 所有真实页面测试均使用无痕模式。
  2. 每个不同账号使用独立无痕浏览器上下文（隔离的无痕 profile）。
  3. 只有同账号多页面测试可以共享一个无痕浏览器上下文。
- 修订后的验证步骤：B、D 分别在独立无痕浏览器上下文登录；依次刷新、退出和重新登录其中一个账号，检查另一上下文中的账号身份、会话和存储模式不受影响。
- 新失败条件：只有相互独立的无痕浏览器上下文之间出现登录态串用，才记录新的会话隔离缺陷。
